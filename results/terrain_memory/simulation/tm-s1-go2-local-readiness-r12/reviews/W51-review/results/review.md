## 3. D0 与 D1 的异常不同，必须分别解释

### 3.1 D0 已刷新当前参考，仍然失稳

D0 的 311 次完成 planner 调用中，272 次 `policy_updated`，其中 256 次为正 homotopy 候选且全部使同问题 J 下降。最后一次更新在 5.800 s，reference 覆盖 `[5.800,6.150]`。全程 2,907 次实际 held 查询，按原物理时钟核对，真正落在 reference 尾部之后的次数为 **0**。

这已经排除“本轮 D0 仍在一直使用 t=0 Stand 参考尾部”这一旧解释。及时刷新和正候选 J 下降在本轮确实发生，但没有自动形成正常支撑与推进。D0 的后段存在强反馈、限位裁剪、QP 投影、实际 held PD 饱和及膝关节反向打限，不能把 D1 的静站问题套在 D0 上。

### 3.2 D1 保住高度，但反馈参考又停留在早期，四足基本不离地

有效 D1 有 421 次完成调用、301 次真实 `Q_is_S`、301 次 S native rollout。安装 116 次中，homotopy 为 94 次，nominal 为 20 次，bootstrap 为 1 次，S 本身直接安装为 1 次。因此“只生成了 S、完全没有搜索”不成立；“S 经常被选中并在执行正常运动”也不成立。

必须区分两个年龄：

| D1 生命周期字段 | 最后一次来源 | 8 s 时年龄 |
|---|---:|---:|
| 当前已安装 policy 的 generation | call 231，4.200 s，`nominal_8` | 3.800 s |
| reference/K/H 的来源 | call 128，2.140 s；reference 结束于 2.490 s | reference 末端已过期 5.510 s |

S 于 call 216 / 3.900 s 被直接安装时，也保留了 `[2.140,2.490]` 的旧 reference。后来 policy ID 或 generation 改变，并不说明参考、K、H 已刷新。4.200 s 之后到 8.000 s，所有调用均保持 incumbent。4.3–8 s 这一段共有 186 次调用，没有一次 policy update。

按同一真实物理时间计，D1 首个明显尾部查询在 **2.492 s**；合计 **2,755/4,001 = 68.86%** 个 held 查询超出 reference_end。8 s 的终端查询没有后续积分；若只计后面确实发生物理子步的 hold，则为 **2,754/4,000**。这项生命周期证据与后段四足完全受载、零接触切换及净后退一致。它说明当前运动搜索没有持续替换出能推进的 incumbent，但还不能仅凭这个关联判定“强制丢弃旧策略”会成功。

### 3.3 `reference_covers_query=false` 不能直接当作过期

原 native 日志中的 RPC 查询时间包含 float32 表示。例如原物理 t=0.020 s，native 记录为 `0.019999999552965164`，略早于 reference_start。它被记为 `covers=false`，但 reference 并未过期。

因此 D0 有 134 条 `covers=false`，真正尾部过期仍为零；D1 有 2,803 条 `covers=false`，真正尾部过期是上述 2,755 条。另有 t=2.490 s 的 float32 查询比 reference_end 多约 9.54 ns，不能把它当作第一条真实尾部执行。独立脚本使用 action-execution 的原物理时钟，并用 1 ns 容差核对；这是审计去除时间表示误差，没有修改控制器或原任务规则。

后续有价值的并行应当是两个互相独立的 CPU 机制问题加一个明确缺口的 GPU 代数/残差工作包。为占显存重复 batch、加无关 PPO 或增加第三条重 native solve，不会解决当前候选不能走的问题。实际运行时可随现有任务低频留存 CPU user/system 累计、GPU utilization/allocated/reserved 与任务身份，不另开吞吐压力测试；这样下一轮才能回答真正消耗了多少核时。

## 8. C 的结果可靠，但范围很小

本审查重新从旧 W50 的六组原 `snapshot.bin.r33-candidates` 读入 114 条残差轨迹，并在 CPU 做原 scalar norm/weight 归约，对照本轮保存的 GPU NPZ。没有重新启动 GPU，也没有重算任何动力学。

复算确认：

- 原始张量形状 `114 × 176 × 113`，22 项，FP64；六组成本定义完全相同。
- 76 条为有效保存问题候选；38 条来自错误 bridge，只能做代数对照。
- GPU/native 总 J 最大绝对误差 `5.820766091346741e−11`。
- CPU/GPU 逐项时间均值最大差 `2.3283064365386963e−10`，逐节点项最大差 `1.4210854715202004e−14`。
- 六组各 19 条，同问题风险/roundoff 规则逐对比较各 361 次，均零差异；总 2,166 次含自比较，不是 2,166 个独立科学试验。
- 原始 roundoff budget 独立复算与保存值完全相同。

状态到残差覆盖应按实际拆分：3 项活动代数项（Upright、Orientation、Posture）已核；6 项 Stand 仅在当前记录的 Trot 分支上为严格零，未证明活动 Stand 分支已实现；MaterialSupportHeight 的 state 近似仍有约 `9.0099e−6` 残差差值，需要准确 native `xpos`；另 12 项尚未从 state/context 重建。

因此本轮交付的是“已保存 native residual → J 的 GPU 归约，加少量状态代数”，没有完整迁移 native cost，更没有把接触求解或 FD/rollout 迁移到 GPU。`complete_native_cost_port=false`、`formal_installation_allowed=false` 是正确结论。设备实际记录为 **NVIDIA RTX PRO 6000 Blackwell Server Edition**，不可沿用旧记忆的 Ada 名称。单批归约约 0.104 s、整个 C 约 0.924 s，且同卡有别的项目，不宜据此作 CPU/GPU 吞吐加速比。
