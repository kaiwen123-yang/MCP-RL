## 2. 异常是怎样传递的

实际调用链：

1. C++ `R29Project` 求当前状态下的 12 维动作投影，并记录解、原始/归一化 KKT 残差和收敛状态。
2. Python `s1_go2_r11_runtime.py` 在执行 `applied_hold`、推进物理前，调用 `R29Records.query`。
3. `metric_valid=true`，但 `qp_converged=false`，因此抛出 `RuntimeError: r29 action unavailable before physics: qp_kkt_failure`。
4. runtime 保存 `reason=execution_error`，协议分类为 `technical_interruption`。
5. 训练循环遇到该分类后退出，保存自己的 resume、optimizer/RNG 和未更新 buffer。

这是同一条明确的技术故障链。A 的故障发生在曾有材料加载之后，B 则从未加载材料，不能把共同退出原因归为材料求解失败。B 的 734 次已记录 planner 调用都安装了策略，未发现这次技术退出前出现长期复用旧计划。

## 3. 为什么不是精度误报，也不是约束无解

原始拒绝行：

| 检查量 | A ep286 | B ep282 |
|---|---:|---:|
| plan id | 594 | 734 |
| metric_valid | true | true |
| 原正则化 μ | 2e-6 | 1e-6 |
| 空区间 / 固定轴 | 0 / 0 | 0 / 0 |
| restoration | false | false |
| 原始可行性残差 | 0 | 0 |
| 最大 KKT 残差 | 0.75750048 | 0.40479570 |
| 归一化 KKT 残差 | 1.1577532e-4 | 3.0654076e-5 |
| 现有容差 | 1e-7 | 1e-7 |
| 超出容差倍数 | 1157.75 | 306.54 |
| native 返回 nfree | 10 | 9 |

12 个瞬时区间均非空，返回动作满足区间边界，但它还没有充分最小化同一个正定二次目标。对

\[
\min_{l\le u\le h}\tfrac12(u-c)^TH(u-c),\qquad g=H(u-c),
\]

自由轴必须有 `g≈0`，下界轴必须有 `g≥0`，上界轴必须有 `g≤0`。B 的若干自由轴仍有明显非零梯度，部分下界轴的梯度符号也不满足最优性。因此，仅检查动作在范围内或者 native `nfree>=0`，都会把尚未收敛的结果当成合格解。

MuJoCo 的实际固定依赖是 `088079eff0450e32b98ee743141780ed68307506`。其 `mju_boxQP` 默认最多 100 次迭代，并采用投影后的 Armijo 线搜索；返回非负自由维数并不保证所有终止路径都已经收敛。源码：[engine_util_solve.c](https://github.com/google-deepmind/mujoco/blob/088079eff0450e32b98ee743141780ed68307506/src/engine/engine_util_solve.c)。本次核对其 `mju_boxQP` 至文件结尾部分与独立安装的 3.2.3 版本源码一致，数值复核不修改 D57 的 MuJoCo。

这里必须分别检查“原生求解器为什么停下”和“投影的最优性是否达标”，不能直接把保护逻辑删掉。RPC 的 float32 序列化确实会产生微小扭矩越界，但它在投影后的另一个环节；原始拒绝依据是 double 精度的 `u_star`，不是序列化后的 `u_held`。

## 4. 修复范围

保留原始、已执行的 `S5-r29` 源补丁与冻结目录。新增独立冻结产物 `S5-r29-qp1`，逻辑控制契约仍为 `S5-r29`，具体二进制、源码和数值修订单独记录。

求解器修复只针对现有证书未通过的同一个 QP：

- 原 native 解通过当前原始可行性/KKT 检查时，返回原动作，不改变它。
- 未通过时，用可行活跃集 Newton 继续求同一个 `H、c、l、h`；在当前自由面求下降方向，只移动到第一个阻挡边界，再按乘子符号释放不应活跃的边界。
- 梯度直接按 `H(u-c)` 计算，固定轴保留交叉项；不改为单位阵、对角近似或原 `Q_ux` 中心问题。
- 完成后重新执行原 `1e-10 rad` 可行性和 `1e-7` 归一化 KKT 检查；仍失败则继续拒绝动作并明确停止。
- 单独记录 native 的状态/残差，以及 refinement 是否发生、迭代数和最终状态。

这是一项数值求解修复，不是新增控制策略、放宽物理约束或恢复旧 r28 动作。正常构建只能创建新的冻结目录，不能覆盖正在或已经执行的原产物。此次没有在 D57 构建、重启主线或运行新物理。

### 同时修复的续跑与可观测性问题

1. **停止原因与退出码。** 技术故障明确保存为 `technical_interruption`，先保存断点再退出码 2；普通物理失败保持续采。异常上下文进入紧凑结果，避免统一写成 `deadline_or_technical_stop`。
2. **失败证据及时上传。** 失败时将该 query 的中心、边界、原始解、梯度、插值 H、q/v 和“尚未推进物理”标记放入小 JSON，并进入 compact result/resolved；不必等待整个原始诊断队列。
3. **无新 update 的旧评价结果。** 显式续跑时，仅将从未有物理 attempt 的 `new_update_unavailable` 管理记录保留到原服务器 job 的小型历史目录。真正启动过的评价不重置时钟、不重复执行。
4. **旧结果快照。** 同 job 续跑后重新收集当前 invocation 的 attempt、采样数、日志和清单；不再沿用第一次退出时的两回合列表。job 根 `collection.json` 使用最终训练快照，修复本次停在 8606/tail13、而真实值已为 8643/8644 的陈旧副本。
5. **GPU 会话匹配。** tmux 查询使用精确会话名，防止查询 `s1-w40` 时被 `s1-w40-gpu` 的前缀匹配误导。恢复两支分别使用 `s1-w40-a`、`s1-w40-b`。
6. **停滞诊断。** 原 `command_nonprogress_2s` 的窗口包含初始站立，2.1 s 时实际只经历约 0.1 s 非零前进命令。修订后零命令会清空窗口，避免把初始站立误标成 2 s 有命令却停滞；它一直只是诊断事件，不是本次停止原因。
7. **拒绝动作身份。** 原代码先分配 `applied_action_id` 再检查 QP，导致被拒绝查询也带有 applied 编号。修订后仅在通过证书时分配，拒绝行保留 null 与 `physics_advanced=false`；历史拒绝行仍按其真实未推进物理解释。

服务器 job 内只保留必要的小型 invocation 历史，未建立用户电脑归档，未删除任何研究输出。当前诊断 manifest 的来源不位于被替换的 `stream-records`，不会因这次续跑快照更新丢失旧上传源；原上传期限不擅自延长。

## 5. 先修技术中断，仍需继续验证物理稳定性

本次已有两个不同层次的问题。共同退出的原因是 QP 技术异常；第一回合的物理失败依然真实存在，修好求解器不能自动宣称 S1 稳定。

对 A285/B281 的原始 5 kHz 物理数组复核显示：在每个 2 ms hold 的第一个子步，raw-PD 超出扭矩界的最大值分别只有约 `5.71e-6 / 5.82e-6 Nm`，与序列化误差量级一致。但同一目标保持到后续子步时，状态已经变化，最大实际 raw-PD 超额分别达到 **20.3179 Nm** 和 **13.7866 Nm**；超额大于 `1e-4 Nm` 的物理行分别为 **285** 和 **115**。

因此，当前状态下的瞬时 PD 可行投影确实发挥了它限定的作用，但没有保证整段十子步、材料有效域和闭环姿态都安全。保持原 2 ms hold/十个 0.2 ms 子步，不能为了绕过这个现象临时改为每子步重算 QP。

A285 在未加载材料时摔倒，最大机身 x 仅 0.652737 m。B281 触发的是原 TM02 2% 有效域退出：FL 足底约 −1.048543 mm、下向速度约 0.451497 m/s、候选主应变约 0.020970864。约 1265.965 N 是被拒绝的材料候选力，不能当作已经施加给机器人的冲击力。

这四个短回合不足以评定 r29 相对 r28 的稳定性收益。恢复后首先观察能否持续采集、完成本支 update34，再按原目标继续到 9617/37；正式能力仍由自己的本轮新 update 的固定 E30、同 case 合格后 E60 决定。
